# Libretro architecture in OpenEmu-Silicon

How a user-installed RetroArch core ends up running inside `OpenEmu.app`, and where in the tree to make changes that affect every libretro core at once.

If anything here drifts from the code, the code wins — fix this doc in the same PR.

---

## TL;DR

A `.dylib` from the user's RetroArch install on disk → an `.oecoreplugin` wrapper generated by `PrefCoresController` → loaded by `OELibretroCoreTranslator` (the **libretro host**) → presented to the rest of the app as an `OEGameCore` → run inside `OpenEmuHelperApp`. There are no libretro cores in this repo; the host runtime exists to load externally-built ones.

---

## How a RetroArch core gets into the app

The picker pipeline in `OpenEmu/PrefCoresController.swift`:

1. **Scan.** `scanRetroArchCores()` enumerates `~/Library/Application Support/RetroArch/cores/`.
2. **Parse metadata.** For each `.dylib`, the matching `<name>.info` file in `~/Library/Application Support/RetroArch/info/` is parsed for display name, supported systems, and capability flags.
3. **Wrap.** When the user picks a core for a system, `installRetroArchPlugin(_:)` generates a synthetic `.oecoreplugin` bundle whose `Info.plist` points to the chosen `.dylib` via the `OELibretroCorePath` key. The bundle is named `<CoreName>-RetroArch.oecoreplugin` (see `RetroArchCore.pluginName`).
4. **Register.** The wrapper lands in the standard cores directory (`~/Library/Application Support/OpenEmu/Cores/`) and from then on is treated like any other core plugin.

The user-facing label is **"RetroArch core"** — that's what they see in Preferences. Internally the abstract concept (any `.dylib` implementing the libretro ABI) is a **libretro core**.

### PlayStation 2

PlayStation 2 is represented by the `PlayStation 2.oesystemplugin` system bundle; it is not an emulator core by itself. The bundle must be built by the `PlayStation 2` target and copied by the OpenEmu target's **Copy System Plugins to App Plugins** build phase. If either link is missing, PS2 won't appear in the Library sidebar even when its BIOS and a compatible RetroArch core are installed. A supported RetroArch core must report `systemid = "playstation_2"` or `"playstation2"` in its `.info` file for the picker to associate it with `openemu.system.ps2`.

The app performs a one-time availability migration for existing libraries when this bundled system plugin first ships. It restores the PS2 entry only once; any later choice to hide the system remains respected.

#### ARMSX2 limitation

The ARMSX2 **libretro** core is not playable through OpenEmu's libretro host. Its metadata declares `hw_render = true` and requires a Vulkan 1.1 context plus the libretro hardware-render context-negotiation interface. The host currently supports OpenGL-family hardware contexts only and deliberately rejects Vulkan, so this variant can start with a black video surface. Its required firmware layout (`system/pcsx2/bios` and `system/pcsx2/resources`) does not change that limitation.

Use the native `org.openemu.ARMSX2` plugin instead when it is installed in `~/Library/Application Support/OpenEmu/Cores/`. It supplies its own `ARMSX2GameCore` and Metal frame callbacks, and is the default PS2 core. Supporting the libretro variant separately would require Vulkan/context-negotiation support in `OELibretroCoreTranslator`.

The native bridge must not synchronously wait for the Metal present command buffer on the GS thread. OpenEmu owns that render loop; a `waitUntilCompleted` at this point deadlocks after the first blank frame, so no `didExecute` callback reaches `ARMSX2GameCore` and the game remains black. `GSDeviceMTL::EndPresent()` instead registers a Metal completion handler, then invokes the callback after the GPU has finished. The bridge also must not call OpenEmu's ordinary `willExecute` callback from PCSX2's GS thread: ARMSX2 already uses the alternate render-thread path. Finally, the generic PCSX2 `FullscreenUI`/`ImGuiManager` calls must be skipped while this bridge is active because OpenEmu deliberately does not initialize PCSX2's ImGui context. The host's Metal texture must declare both `MTLTextureUsageShaderRead` and `MTLTextureUsageRenderTarget`: ARMSX2 renders into it, then OpenEmu samples it for presentation. The game core can safely read back the completed texture and deliver it to OpenEmu from the completion callback.

#### Validated PS2 black-screen resolution

The native `org.openemu.ARMSX2` plugin was validated with PS2 games after applying all of the following together:

1. Build and install the native ARMSX2 plugin; do not select the Vulkan-only RetroArch variant.
2. In `GSDeviceMTL`, submit the OpenEmu present command buffer and call the bridge's `didExecute` callback from its completion handler. Do not block the GS thread with `waitUntilCompleted`.
3. Treat ARMSX2 as an alternate-thread renderer: do not call the normal OpenEmu `willExecute` callback from PCSX2's GS thread, and skip PCSX2 ImGui presentation calls while the bridge is active.
4. Create the host `metalTexture` with both `MTLTextureUsageShaderRead` and `MTLTextureUsageRenderTarget`. The former is required for OpenEmu presentation; the latter is required for ARMSX2's Metal render pass.

After changing the host texture descriptor, rebuild and launch OpenEmu from Xcode so the corrected host executable is used. After changing the ARMSX2 bridge, rebuild `armsx2_libretro.dylib`, replace only `ARMSX2.oecoreplugin/Contents/Resources/armsx2_libretro.dylib`, and re-sign the plugin. A successful frame path logs `OpenEmu present encoding`, `EndPresent submitted`, `OpenEmu present completed`, and `Metal readback frame` in `/tmp/openemu-armsx2-metal.log`.

## The `.oecoreplugin` wrapper

It's a normal macOS bundle. The relevant Info.plist fields:

| Key | Purpose |
|---|---|
| `CFBundleIdentifier`, `CFBundleName` | Standard bundle metadata |
| `OEGameCorePluginClassName` | Points to the libretro host class |
| `OELibretroCorePath` | Absolute path to the user's external `.dylib` |
| `OEGameCoreSystemIdentifiers` | Which OpenEmu systems this core handles |
| `OEBridgeVersion` | Version stamp matching `OELibretroBridgeVersion` at install time. On app launch, `refreshStaleRetroArchStubs()` compares this against the running app's value and refreshes the stub's executable if they differ. |

The host app's plugin loader doesn't care that the binary is wrapped — it loads the bundle, instantiates the plugin class, and the plugin class is the libretro host configured to `dlopen` the `.dylib` at the recorded path. The stub's own `Contents/MacOS/` executable is a copy of the OE-side translator binary (the **bundled libretro bridge**, see below), seeded by `PrefCoresController._createPlugin` at install time and refreshed automatically on every app launch.

## The libretro host (`OELibretroCoreTranslator`)

`OpenEmu-SDK/OpenEmuBase/OELibretroCoreTranslator.m` (~1,990 LOC). Subclasses `OEGameCore` and implements the libretro ABI on the inside, OpenEmu's renderer/input/audio interfaces on the outside. Key entry points:

| Method | Line (approx.) | Role |
|---|---|---|
| `-loadFileAtPath:error:` | 982 | `dlopen` the libretro `.dylib`, call `retro_init` / `retro_load_game`, query memory and AV info |
| `-executeFrame` | 1192 | One `retro_run` tick + AV/input marshalling |
| `-stopEmulation` | 1179 | `retro_unload_game` / `retro_deinit`, tear down |
| Env callback dispatch | (internal) | Handles `RETRO_ENVIRONMENT_*` requests from the core |

Cross-cutting libretro features go here, **once**. That is the entire reason the host exists.

## Bridge propagation: auto-refresh on launch

Each installed `*-RetroArch.oecoreplugin` stub carries its own copy of the translator binary in `Contents/MacOS/`. Without a propagation mechanism, every fix to `OELibretroCoreTranslator` would require users to reinstall every RetroArch core they have set up. The bundled bridge plus the launch-time refresh closes that gap.

Two version constants drive the comparison:

- `OELibretroBridgeVersion` — defined in `OELibretroCoreTranslator.m` (and externed in the matching `.h`). The running app's value, baked into the binary at build time. Bump this whenever you change `OELibretroCoreTranslator`.
- `OEBridgeVersion` — a per-stub stamp written into each `*-RetroArch.oecoreplugin/Contents/Info.plist` at install time and overwritten whenever the stub is refreshed.

Lifecycle, in order:

1. App launches. `applicationWillFinishLaunching` (in `OpenEmu/AppDelegate.swift`) calls `refreshStaleRetroArchStubs()`.
2. The function walks `~/Library/Application Support/OpenEmu/Cores/` for every `*-RetroArch.oecoreplugin`.
3. For each stub whose `OEBridgeVersion` is missing or `!= OELibretroBridgeVersion`, it copies `OpenEmu.app/Contents/PlugIns/OpenEmuLibretroBridge.oecoreplugin/Contents/MacOS/OpenEmuLibretroBridge` over the stub's executable, writes the new version into the stub's plist, and ad-hoc codesigns the result.
4. Outcomes (which stubs were refreshed, which failed and why) are summarized in `~/Library/Logs/OpenEmu/core-inventory.txt` per launch.

Initial install path: `PrefCoresController._createPlugin` (in `OpenEmu/PrefCoresController.swift`) seeds the stub's executable from the bundled bridge and stamps `OEBridgeVersion` at the same time. As a transition-period safety it falls back to a translator binary copied from an installed native core if the bundled bridge isn't present on disk yet.

```
OpenEmu.app/
  Contents/
    PlugIns/
      OpenEmuLibretroBridge.oecoreplugin/      ← shipped with the app
        Contents/MacOS/OpenEmuLibretroBridge   ← source binary

~/Library/Application Support/OpenEmu/Cores/
  Flycast-RetroArch.oecoreplugin/              ← user-installed stub
    Contents/
      Info.plist                               ← OEBridgeVersion lives here
      MacOS/Flycast-RetroArch                  ← copy of the bridge binary, refreshed at launch
```

Developer-facing rule (when to bump `OELibretroBridgeVersion`) lives in the "Libretro Bridge Version Bumps" section of `AGENTS.md`.

## What the host handles today, and what it does not

**Handles:**
- libretro ABI translation (`retro_run`, AV callbacks, input device descriptors)
- audio/video bridging into OpenEmu's renderer + audio queue
- input bridging (controller mapping, keyboard, hotplug)
- save state passthrough via `retro_serialize` / `retro_unserialize`

**Does not handle yet:**
- **RetroAchievements.** No `rc_client` initialization, no per-frame `rc_client_do_frame`, no memory exposure to rcheevos. Tracked in [#360](https://github.com/nickybmon/OpenEmu-Silicon/issues/360). Native cores integrate rcheevos directly; libretro cores get nothing.
- **`RETRO_ENVIRONMENT_SET_MEMORY_MAPS` (env callback 36).** Cores that expose RAM via descriptor tables rather than `retro_get_memory_data` are not currently mapped — verify before doing memory-dependent work (cheats, RA).
- **Runahead.** No frontend-side state-rollback loop.

## When to reach for a native core instead

Rule of thumb: if the user can install a working RetroArch core for the system, the host runtime is the right path. Reserve native cores (subclassing `OEGameCore` directly) for systems where in-tree control of the frame loop is necessary — currently RetroAchievements, anti-cheat behavior, and OE-specific features the libretro ABI doesn't expose. Adding a new in-tree libretro core is almost never the right answer; extend the host instead.

## Historical: bridge cores

Earlier in development the tree contained `Flycast-Bridge/`, `Gambatte-Bridge/`, and `VICE-Bridge/` directories holding pre-compiled libretro binaries used to test the host runtime. They were never shipped to users, never referenced by the Xcode project, and were removed in May 2026. They are mentioned here because older PRs and commits still refer to them. The current pathway for any libretro work is the host runtime plus the RetroArch picker — do not reintroduce in-tree libretro binaries.
